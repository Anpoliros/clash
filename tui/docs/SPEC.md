# Docs Spec

本文档定义 `clash-tui` 文档的写作规范、模板和更新规则。它面向维护者和 coding agent，优先服务 `/tui` 的后续开发。

## 核心原则

- 文档服务于修改代码，而不是复述代码。
- 优先记录稳定约定：模块职责、外部 API、数据模型、运行流程、生成产物、验证方式和风险边界。
- `clash-tui` 是 Runtime First 客户端，文档应明确哪些操作发生在 mihomo 运行态，哪些操作会写入 `runtime.yaml`。
- 用户原始 mihomo 配置是保护对象。任何会影响 `config.yaml`、订阅缓存或工作目录文件的改动，都要在文档中写清楚。
- 不为每个小文件写文档；只有核心模块、公共接口、关键流程和容易误改的地方需要独立文档。
- 修改核心逻辑时，同步检查相关文档和 `docs/MAP.md`。

## 文档类型

### 入口文档

入口文档说明文档系统如何使用，例如：

- `docs/README.md`
- `docs/MAP.md`
- `docs/SPEC.md`
- `docs/init.md`

### 架构文档

架构文档记录系统整体视角、数据流和外部边界，例如：

- `docs/architecture/overview.md`

### 模块文档

模块文档描述一个目录、功能域或核心能力，例如：

- `docs/modules/core.md`
- `docs/modules/mihomo-api.md`
- `docs/modules/runtime-config.md`
- `docs/modules/ui-interaction.md`

### 流程文档

流程文档描述开发、构建、发布、运行和排障等工程操作，例如：

- `docs/workflows/development.md`
- `docs/workflows/release.md`

### 决策文档

决策文档记录重要背景和取舍，适合放在 `docs/decisions/` 中。命名建议使用递增编号：

```txt
docs/decisions/0001-runtime-first.md
docs/decisions/0002-runtime-config-location.md
```

## 模块文档模板

核心模块至少包含“模块视角”“实现视角”“修改指南”和“验证方式”。没有内容的章节可以省略。

```md
# {模块名}

一句话说明这个模块负责什么。

## 模块视角

说明模块职责、使用场景、对外行为和不负责的边界。

## 实现视角

说明入口文件、关键文件、核心函数、公共接口和依赖关系。

## 数据模型

说明核心类型、字段含义、默认值、约束和兼容要求。

## 修改指南

说明常见改动应该从哪里开始，哪些文件需要一起看，哪些边界不要轻易突破。

## 验证方式

说明修改后应该运行的命令、检查的页面、构建产物或人工确认点。

## 相关文档

- `docs/MAP.md`
- 其他相关文档
```

## 流程文档模板

```md
# Workflow Name

一句话说明这个流程用于什么场景。

## 触发场景

说明什么时候需要运行或修改这个流程。

## 输入与产物

说明输入文件、环境变量、命令参数和生成产物。

## 执行步骤

1. 第一步
2. 第二步
3. 第三步

## 常见问题

记录容易误判的失败原因和排查入口。

## 验证方式

说明如何确认流程成功。
```

## 决策文档模板

```md
# 0001 Decision Title

## 背景

说明当时为什么需要做这个决策。

## 决策

说明最终选择了什么方案。

## 取舍

说明收益、成本、风险和暂未解决的问题。

## 影响范围

列出受影响的源码路径、文档路径和工作流程。
```

## 更新规则

以下情况必须检查并视情况更新文档：

- 新增、删除或重命名 `/tui/src` 下的核心目录。
- 修改 CLI 参数、启动流程、工作目录发现或 mihomo 二进制发现。
- 修改 `runtime.yaml` 生成位置、字段、默认值、TUN 写入逻辑或用户配置保护策略。
- 修改 mihomo external-controller API、认证、请求超时、WebSocket 日志、测速 URL 或 Provider 刷新逻辑。
- 修改 Proxy/TUN 开关、sudo 验证、PID 文件、子进程环境变量隔离或日志捕获。
- 修改 `AppEvent`、应用状态结构、页面状态、快捷键、鼠标点击区域或 UI 布局。
- 修改 Cargo 依赖、feature、Rust edition、开发命令或验证流程。
- 修复一个依赖隐含知识的问题，且该知识未来可能再次影响维护。

以下情况通常不需要更新文档：

- 小范围样式或配色调整，且不改变交互和页面职责。
- 内部函数重排，且不改变入口、状态模型、外部行为和验证方式。
- 只修正错别字、日志文本或无行为变化的状态提示。

## MAP.md 维护规则

`docs/MAP.md` 是文档系统的索引，应保持简洁和准确：

- 新增核心源码路径时，为它添加对应文档或建议文档路径。
- 删除源码路径时，同步移除或改写映射。
- 重命名源码路径时，同步更新 `Source Path`。
- 新建模块文档时，把 `Documentation` 从建议路径更新为实际路径。
- 同一个源码路径可以对应多个文档，但不要把同一个文档映射到过多无关路径。

## 写作风格

- 使用中文，语气清晰、直接、现代。
- 优先使用短段落和表格，减少长篇叙述。
- 文件路径、命令、类型名和函数名使用反引号。
- 解释“为什么这样设计”和“修改时要注意什么”，避免逐行解释源码。
- 对 agent 重要的信息要显式写出：入口文件、影响范围、验证命令、不要改动的边界。
- 源码注释继续遵循项目要求：简要中文注释，必要时使用 `#----xxx----` 划分模块。
